# ADR 0014: Scanning a repository for tests that verify nothing

Status: accepted. Makes one exception to the hiding rule of ADR 0003, for the
output of a scan only. Every other part of ADR 0003, and ADR 0005 and 0013, stands.

## Context

The proof modules need a spec whose criteria carry `ID~REVISION`, and their proofs
gate a change. Most repositories have no such spec. `spec-proof scan` runs on any
repository or change without one and prints one number at once: how many of the
sampled tests still pass when the code they run is broken, with the broken code
that shows it.

Two things must keep their credibility at that scale: no false pass, and no
finding without an executed fact behind it. The design was decided by a debate
between an execution-first and a promise-first position, with a judge who checked
the decisive claims against the code and the pilot's data
(`notes/debates/debate-scan-verdict.md`).

## Decisions

### What a scan runs

- **Modes.**
  - In repository mode, the default, the scan samples tests by a seed,
    stratified by file: 12 in the default quick scan, 40 with `--full`.
  - A quick scan gives a first number within a 90 s budget. Where each test
    runs alone under coverage, as in Go, it records the coverage of its sampled
    tests only, so only they run a mutant; `--full` records the coverage of
    every green test and has no budget.
  - In change mode (a branch ahead of the default branch, or `scan <PR>`), it
    takes the functions the change edits and the tests that run them.
  - The ecosystem's `Detect` picks the runner.
- **What is never mutated.** Tests, vendored and generated files, migrations, and
  sink calls such as logging, printing and metrics.
- **Mutants.**
  - The operator generator draws 150 mutants (72 in a quick scan) from the
    catalogue of ADR 0003, constants included. They are allocated round-robin over the lines the sampled
    tests own (see "The claim"), so that each test gets the mutants its claim
    needs before any test gets more. At most 12 sentinels are added, stratified
    by file.
  - With a host, up to 20 model mutants are added, steered by the promises and
    stored as edit sets.
  - Compiled-form identity (E0) drops a mutant whose every edited site compiles
    to the reference's form. In Go, a mutant whose edited sites all lie in one
    package is compiled against the listing and the import configuration that
    package's first compile read: a change confined to one package leaves its
    dependencies as the reference has them. Sites that span packages are read
    afresh.
  - Equivalence is never judged.
- **Runs.** Every test runs three times on the reference. A test is **green**
  when it passes all three runs. Each mutant runs, three times, against every
  test whose coverage includes one of its mutated lines, start-up included.
  - **One observation is one process.** A run is one process that starts the
    test. In Go the three runs of a package start as one `go test -count=3`
    process; when that process exits non-zero without timing out before a test
    had three end events, it counts as one run of each test of the package,
    each test taking its first end event, and the package runs again in fresh
    `-count=1` processes until every test has three runs. A test that panics
    in its own body therefore fails three runs, and the tests before it pass
    theirs.
  - **A run that did not start.** A run is `not_started` only on positive
    evidence that its process stopped before any test began:
    - in Go, the process exited non-zero without timing out, the package's
      binary ended in a failure, no event names a test of the package and no
      event reports a build failure;
    - in pytest, the test has no outcome and a failed collect report covers its
      module, or a `conftest.py` or `__init__.py` on its path.

    A run missing without that evidence, a fixture or setup error, and a
    session that ends in a usage, internal or interruption error without such
    a report are errors.
- **Settled outcomes.** The three runs of a test on a mutant settle as:
  - **killed**: all three fail;
  - **survived**: all three pass;
  - **not_started**: all three did not start. The pair counts neither for nor
    against the test (see "The claim");
  - **inconclusive**: anything else. A timeout, an error, a missing run, runs
    that disagree and any mix with a run that did not start count as neither a
    kill nor a pass.

  A test with a reference run that did not start is not green. A run that did
  not start on a sentinel is no failure: it neither disqualifies the test nor
  counts, and the report counts the sentinels that stopped a test binary as a
  fault of the harness.

### A proven behaviour change

A mutant counts only when executed evidence proves that it changes behaviour.
A mutant without a route is unproven, and an unproven mutant never counts for or
against any test. There are three routes:

| Route | Executed evidence |
|---|---|
| `killed_by_test` | A test of the suite kills the mutant 3/3. The test is green and fails no run on any sentinel. |
| `f3_difference` | A full-resolution differential search finds an input of an operation on which the mutant's result differs from the reference's; the route names the operation and the input. The difference must reproduce, and the reference must agree with itself on that input. Inputs are seeded from the literals of the suite. Only a return value, a raised exception or a mutated argument is compared, never logs or the standard output. |
| `witness_failure` | An admitted G3-W witness, written blind to every mutant, fails on the mutant, reproduced. |

A sentinel keeps behaviour by construction and is never proven.

### The claim

The coverage of a test is per line: the lines its run executed, the start-up of
its process included. A test runs a mutant when its coverage includes one of the
mutant's mutated lines. The **site** of a mutant is its first mutated line, by
file and then line number.

A test **owns** the lines it ran itself, beyond the start-up of its process:
- in Go, coverage binaries count blocks in atomic mode, each binary runs once
  with `-test.run='^$'` to count its start-up, and a test owns a block whose
  count exceeds that count; a test whose binary gives no start-up count owns
  no line;
- in pytest, coverage records only inside each test's setup, call and
  teardown, never during collection, so every recorded line is owned.

Dispatch reads the whole coverage; the allocation's quota reads owned lines
only.

The **pairs** of a test are the proven mutants it runs, each with the test's
settled outcome on it. A pair counts by its outcome and by whether the test owns
one of the mutant's mutated lines:

| Settled | Owned line | Start-up-only line |
|---|---|---|
| killed | change | change |
| inconclusive | change | change |
| survived | change | ignored |
| not_started | listed apart | ignored |

Only a survival needs ownership. A line a test ran only at start-up therefore
never feeds a claim that it verifies nothing, yet still records a kill and still
blocks that claim when its outcome is inconclusive, so that a non-pass never
stands in for a pass. A pair listed apart stopped the test from starting: it is
never a change, a kill, a survival or a route.

The **changes** of a test are its pairs that count as changes. A sampled green
test is classified in this order:

1. **Unproven, kills a sentinel.** It failed a run on a sentinel. Its outcomes
   do not tell behaviour from form, so it is never said to verify nothing or to
   catch a change.
2. **Caught at least one change.** It kills one of its changes.
3. **Verifies nothing.** It survives every one of its changes, there are at least
   `R_min = 5` of them, and they lie on at least 2 sites.
4. **Unproven, inconclusive outcome.** It has an inconclusive outcome on one of
   its changes. Such a change is neither caught nor survived, so a timeout can
   never stand in for a pass.
5. **Unproven, too few changes.** Every other test.

Every test of the suite falls into exactly one of five classes:

- verifies nothing;
- caught at least one change;
- unproven;
- not sampled: green, but not drawn;
- not green: no verdict at all.

**The denominator** of "verifies nothing" is the sampled green tests: the sum of
the first three classes. The scan always prints the full split:

> verifies nothing / caught ≥ 1 / unproven / not sampled

This keeps the complement of the claim from reading as a pass.

For each test that verifies nothing, the scan prints one literal sentence:

> passes on all N proven changes in lines it ran

with one change, its input and its route. When k proven changes stopped the test
from starting, the sentence continues "; k more stopped it from starting". Each
other judged test that k proven changes stopped from starting gets the line
"k proven changes in lines it ran stopped it from starting; they count neither
way".

**Banned words.** A scan never prints "bug", never prints PASS, and never prints
a score that a clean run could be read from. A scan that finds nothing still
prints the split, and the unproven and unsampled tests stay unjudged.

The domain package `discpower/internal/domain/vacuity` holds these rules, with no
I/O. Its output does not depend on the order of its input. It ranks tests:

- verifies nothing first, then caught, then unproven;
- within a class, by number of changes, most first;
- then by test id, byte-wise.

### Promises: labels, and one gated finding

- **Extraction.** With a host, one ticket extracts promises from the README, the
  change's description and the issues it closes. Each promise carries a quote
  and its source.
- **Quote check.** A deterministic check keeps a promise only when its source
  still has the digest the promise records and contains the quote byte for byte
  (`format.CheckQuote`).
- **Labels.** A promise labels the tests whose changes may break it. A label
  never creates, removes or changes a verdict.
- **Witnesses.** Each kept promise gets G3-W witnesses, written blind to every
  mutant, with the admission and the two scope tickets of ADR 0013. A witness
  the reference fails becomes a question about the promise, never a finding.
- **Broken promise.** This is the one finding a promise can carry. It needs a
  mutant that:
  - fails, reproduced, a block-bearing witness of the promise;
  - passes the whole suite three times.

  The scan prints it with the quote. Judgment only gates the scope of the
  witness; it never creates the finding.
- **Without a host.** The scan prints the full headline, then "promises not
  checked".

### The binary never calls a model

The scan binary never spawns a harness and never opens a model connection.
- **Model work.** Promises, model mutants, witnesses, scope and labels are host
  tickets of ADR 0005. The `/spec-proof:scan` skill drives them through the
  exit-3 loop and `--resume`.
- **Budget.** At most 18 calls per scan:

  | Use | Calls |
  |---|---|
  | promises | 1 |
  | generation | 4 |
  | witnesses and scope | 4 for each of at most 3 promises |
  | labels | 1 |

- **Replay.** `spec-proof scan replay DIR` re-executes every claim of a scan with
  no model. Model mutants are stored as their edits.

### The scan statement (`scan/v1`)

A scan is recorded as an in-toto Statement v1 with the predicate type
`https://rachid-chabane.com/attestations/scan/v1`. The `format` module defines it
and reuses the format's canonical encoding, digests and DSSE envelope.

- **Subject.** The subject is the scanned commit, with the file-set digest of its
  tree.
- **Predicate.** The predicate holds:
  - the module and its version, the producer, the mode and base commit, the
    runner and the seed;
  - whether the budget stopped the scan, and whether promises were checked;
  - the counts of the five classes;
  - every mutant with its edits, mutated lines, origin and routes;
  - every sampled green test with its class, its reason when unproven, its
    settled outcome on each change and, apart, the proven mutants that stopped
    it from starting (`notStarted`);
  - with a host: the promises with their quotes and source digests, the
    witnesses, the broken promises and the questions.
- **Mutant id.** It is the digest of the mutant's edits, the same digest
  `discpower` gives the edit set.
- **Validation.** The format checks the structure:
  - sort orders, digests and closed sets;
  - that the counts add up to the suite and match the listed verdicts;
  - that a test cites only proven mutants that are not sentinels, among its
    changes and among the mutants that stopped it from starting, and never one
    mutant in both;
  - that a test which verifies nothing survived every change it cites, and a
    caught test killed one;
  - that a broken promise rests on a block-bearing witness its mutant fails.

  R_min and the classification order belong to the domain, not to the format.

### The gate refuses a scan statement

A scan statement is never a proof of a requirement:
- **No requirement.** It has no `requirement` member: the format reports one,
  and the scan schema refuses it.
- **No kind.** Its predicate type is no proof kind: `format.Decode` and
  `format.Admit` return `ErrUnknownPredicateType`, as do the module schema checks.
  The ledger and the verifier therefore refuse it, and Shallnot's reader ignores
  it.
- **A golden vector** among the proof vectors holds a valid scan statement and
  states that refusal for every reader that runs them, Shallnot's included.

**Why Shallnot must refuse it.** A scan:
- infers its criteria from text no owner wrote as a spec;
- samples tests rather than binding them;
- may show its mutant bodies.

If the gate admitted it, a synthesized criterion could pass or block a change
with none of the binding, traceability and hiding a proof needs. A scan answers
"which of these tests check nothing", never "does this change meet its
requirements".

### Exception to the hiding rule of ADR 0003

**The rule.** ADR 0003 keeps mutant bodies out of every proof and every finding,
so that a test cannot be fitted to the mutants the gate will use.

**The exception.** A scan shows its bodies, because the broken code is the
finding:
- `mutant.patch` and `repro.sh` in each finding folder;
- the edits in the scan statement.

**Why this is safe.**
- **Scan proofs never gate.** The gate refuses them.
- **Scan seeds are disjoint from gate seeds.** A scan draws from its own seed,
  never from the seed of a head commit or a CI run.
- **The gate redraws.** It draws fresh seeded operator mutants, fresh sentinel
  kinds and positions, and fresh targeted mutants.

A test fitted to the mutants a scan showed has done real testing work at those
sites. Under the gate's draw it earns nothing it would not have earned otherwise.

### Output and placement

- **Output.** `.spec-proof/scan/<sha>/` holds `report.md` and one folder per
  finding with:
  - `mutant.patch`;
  - `repro.sh`, which checks out the commit, applies the patch and runs the one
    test, which passes;
  - the route that proves the change;
  - a host-written killing test, kept only when it kills the mutant and passes
    the reference.
- **Formats.** `--format md` writes a pull-request comment; `--format json`
  writes the scan statement.
- **Placement.**
  - `discpower` holds the pure `domain/vacuity`, the `app/scan` use case and the
    `spec-proof-dp scan` command.
  - `umbrella` holds the `spec-proof` dispatcher.
- **Targets.** A quick scan aims at a first number within 1 to 2 minutes. For a
  full scan of a suite that runs in at most 60 s, with no model:

  | Runner | Target |
  |---|---|
  | pytest, Go | 6 minutes |
  | Vitest, Jest | 8 minutes |
  | Maven, Gradle | 15 minutes |

  - A host adds at most 10 minutes.
  - `--budget` stops the scan with partial counts, marked `partial`.
  - Runs are `nice`d, on at most 4 workers chosen from the processors and the
    memory above the memory guard's free share, in workspaces outside the work
    tree.

## Consequences

- Any repository gets a number without a spec, a model or configuration. Every
  test it names rests on executed evidence that a reader can replay.
- A test is named only on proven changes. A suite whose mutants no route proves
  yields "unproven", never "verifies nothing".
- A sentinel-killing test, and any test with an inconclusive outcome on one of
  its changes, falls under "unproven". The headline undercounts rather than
  overclaims.
- Per-line coverage per test must be measured in each ecosystem, with
  instrumentation shipped with the tool and applied only in the workspace.
  Function-level coverage would blame a test for lines it never ran.
- Scan output shows mutant bodies; gate output never does. The two never share a
  seed or a proof.
- Promises add explanation and one gated finding, never a pass. A scan does not
  measure the validity of G3-W, so a broken promise always shows its quote and
  its witness for the reader to check.
